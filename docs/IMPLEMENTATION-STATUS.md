# Implementation Status

Live snapshot of design vs. reality — updated as code lands, not retroactively rewritten.
Companion to [`PROGRESS.md`](PROGRESS.md) (the "how we got here" log) and to `docs/ROADMAP.md`
(the phase plan). The design docs (`WHITEPAPER.md`, `docs/*`) describe intent; this table says
what actually exists in the repo right now, and where.

> **"Done" means implemented and unit-tested in this repo — it does not mean audited.** Per
> `docs/CRYPTOGRAPHY.md` §9 and `docs/GOVERNANCE.md` §3, no security claim ships to general
> availability without an independent external audit. Nothing here is a GA claim.

| Noise `XX` handshake | `CRYPTOGRAPHY.md` §4.1 | ✅ | `core/src/crypto/noise.rs` | 1 test; interactive (both-in-range) case only |
| Noise → Double Ratchet handoff | `CRYPTOGRAPHY.md` §4.1/§5 | ✅ | `core/src/crypto/session.rs` | 2 tests; the glue that was missing — handshake transcript hash seeds the ratchet, responder's fresh ratchet pubkey delivered as one Noise-transport-encrypted message |
| Prekey async bootstrap (X3DH-style) | `CRYPTOGRAPHY.md` §4.2 | ✅ | `core/src/crypto/prekey.rs` | `SignedPrekey`/`OneTimePrekey`/`PrekeyBundle` + `initiate`/`respond` computing the 3-or-4-DH X3DH shared secret (HKDF-SHA256, 0xFF-padded per spec). | MLS groups (RFC 9420) | `CRYPTOGRAPHY.md` §6 | ✅ | `core/src/groups.rs` | **Not hand-rolled — uses the `openmls` crate** (pure-Rust `openmls_rust_crypto` backend, no C/OpenSSL toolchain risk), a deliberate choice given TreeKEM/epoch-state complexity is a different order of magnitude from this project's hand-rolled primitives (Noise, Double Ratchet) — see the module doc comment for the full reasoning. Ciphersuite `MLS_128_DHKEMX25519_CHACHA20POLY1305_SHA256_Ed25519` (matches this project's other primitive choices). Group creation, add-member (KeyPackage/Commit/Welcome), joining via Welcome, and application messages all exercised through real wire serialization. 5 tests incl. a 3-member scenario and tamper rejection. **Not done:** durable persistence (openmls's storage is in-memory only — a restart loses all group state), routing integration (MLS ciphertext isn't carried as `Envelope`s through `RelayEngine` yet), UniFFI export (not reachable from Kotlin/Swift yet), member removal/self-update/external-commit paths. Small-group per-member-copy fallback (`CRYPTOGRAPHY.md` §6) also still unwired |
| Channels (Argon2id passphrase key) | `CRYPTOGRAPHY.md` §6 | ✅ | `core/src/crypto/channel.rs` | `Channel::from_passphrase` derives both the secret AEAD key and the public `Addressing::Channel` routing selector from one Argon2id call (via `crypto::passphrase`, shared with duress) + HKDF domain-separated expansion. **Unlike duress's random salt:** the Argon2id salt here is deterministic (`BLAKE3("MESH_CHANNEL_SALT" || passphrase)`), because two strangers who only share a spoken passphrase must independently derive the identical `(key, selector)` pair with no other coordination — a channel's entire trust model. `seal`/`open` wrap the existing many-use AEAD (`crypto::aead_seal`/`aead_open`), selector bound in as associated data. 6 tests incl. two independently-constructed `Channel`s from the same passphrase matching exactly, and a wrong-passphrase-guess failing to open. **Not done:** no envelope-composition helper wiring `Channel` into `Envelope::new(Addressing::Channel(selector), ...)` end to end yet (mechanical, not attempted this pass), no UniFFI export |
| PQXDH / post-quantum hybrid handshake | `CRYPTOGRAPHY.md` §6a | ✅ | `core/src/crypto/pqxdh.rs` | Builds on `crypto::prekey` rather than replacing it: `HybridBundle` = classical `PrekeyBundle` + a signed ML-KEM-1024 (FIPS 203) encapsulation key (new `PqPrekey`, via the `ml-kem` crate — RustCrypto, pure Rust, same "don't hand-roll a security-critical PQ construction" call already made for MLS/TreeKEM). `initiate`/`respond` run classical X3DH and an ML-KEM encapsulation/decapsulation side by side and combine both secrets in one HKDF (`classical_secret \|\| ml_kem_shared_secret`) — secure if *either* half holds, per the doc's hybrid requirement. Real API verified via docs.rs/GitHub source before writing integration code (matching this project's openmls precedent), then confirmed via actual compiler errors for the exact method names (`generate_keypair_from_rng`, `encapsulate_with_rng`, `KeyExport::to_bytes`) — several guesses from the docs summary were wrong and caught this way, not shipped. Needed a second RNG crate (`rand` 0.10, aligned with `ml-kem`'s `rand_core` 0.10 requirement) alongside the existing `rand_core` 0.6 used everywhere else in this crate — the two coexist fine since nothing needs to pass an RNG value across that boundary. 4 tests incl. a full hybrid-bootstrap-to-ratchet-messaging round trip and a tampered-PQ-signature rejection. Release build reconfirmed successful with the new dependency tree. **Honest limit, stated in the module doc and matching `CRYPTOGRAPHY.md` §6a exactly:** stops a passive harvest-now-decrypt-later adversary; does not stop an active quantum attacker forging Ed25519 signatures — not a "quantum-proof" claim. **Not done:** not exported over UniFFI, no key-rotation/pool management for `PqPrekey` (same gap `crypto::prekey`'s classical `SignedPrekey` already has) |
| Metadata: link-identifier rotation | `CRYPTOGRAPHY.md` §7.1 | ⬜ | — | belongs at native radio-driver layer |
| Metadata: envelope size bucketing | `CRYPTOGRAPHY.md` §7.2 | ✅ | `core/src/crypto/padding.rs` | `pad_to_bucket`/`unpad` operate on **plaintext before sealing**, not as an `Envelope` wire-format field — padding ends up inside the ciphertext, so the wire-visible effect (every envelope in a bucket has equal `sealed.len()`) falls out of AEAD's fixed overhead automatically, with zero changes to `envelope.rs`'s wire format or hop-stable ID logic. 6 buckets (64B .. 64KiB), a reasoned-not-benchmarked log-ish progression covering short text through voice-note-sized payloads; large media is expected on Wi-Fi Direct per `FEATURES.md` §6, not bucketed BLE envelopes. Oversized plaintext is rejected, not silently truncated. 6 tests. **Not done:** not wired into any actual message-composition call site yet (no caller pads before calling `aead_seal`/`Channel::seal`/ratchet `encrypt` today) — this pass is the primitive, wiring it into every sealing call site is a follow-up |
| Sphinx onion routing (optional) | `CRYPTOGRAPHY.md` §7.3 | ⬜ | — | Phase 2 per roadmap |
| Encryption at rest | `CRYPTOGRAPHY.md` §8 | ✅ | `core/src/persistence.rs` | **deviation from doc, flagged:** `redb` (pure-Rust) + our ChaCha20Poly1305 AEAD, not literally SQLCipher — `rusqlite`'s SQLCipher backend needs OpenSSL compiled from source, which failed repeatedly on this project's Windows dev box even with MSVC + Strawberry Perl (see `PROGRESS.md`). Same security property (AEAD encryption at rest, tamper-evident), different engine. 4 tests + 2 FFI-layer tests. Revisit real SQLCipher if a working OpenSSL build environment (e.g. Android NDK's) becomes available |
| Duress / panic-wipe | `CRYPTOGRAPHY.md` §8 | ✅ | `core/src/persistence.rs`, `core/src/durable.rs`, `core/src/crypto/passphrase.rs` | `EncryptedStore::wipe`/`DurableStore::wipe`: best-effort secure delete (overwrite-then-remove) of the on-disk database file, consuming `self` first so the handle isn't held open (matters on Windows). No "duress mode" concept added anywhere — a decoy state is just an ordinary `DurableStore::open` at a different path with a key derived (via the new `crypto::passphrase` Argon2id module, shared with Channels) from a different passphrase; which passphrase maps to which (path, key) is native-layer/UX policy, not tracked here. 6 new tests (2 wipe, 4 passphrase-derivation). **Honest limit, stated in the code:** overwrite-then-delete is not a guarantee against flash/SSD wear-leveling retaining old physical blocks — defense in depth on top of destroying the key itself (native-layer job, e.g. deleting an Android Keystore alias), not a standalone forensic guarantee, matching `THREAT-MODEL.md` §2 (A5)'s existing "mitigations, not guarantees" framing. **Not done:** no native-layer UI/flow for triggering panic-wipe or setting a duress passphrase yet |

| Bloom-filter summary vectors | `ROUTING-PROTOCOL.md` §7.1, §3 | ✅ | `core/src/bloom.rs` | Hand-rolled `BloomFilter` (double hashing off a single BLAKE3 digest, no new dependency), sized via the standard `m`/`k` formulas. `Store::summary_bloom`/`missing_from_bloom` and `relay.rs`'s `ContactMessage::Summary` now use it on the wire (`Store::summary_ids`/`missing_from` exact-set versions kept for callers that want an exact diff). 5 tests: no-false-negatives, empty-filter, empirical false-positive-rate bound, wire roundtrip, malformed-input rejection. **Not implemented:** the doc's "small explicit recent-ID list to bound false positives on hot items" — a very-recently-composed envelope can, rarely, be skipped by a peer's false positive; self-heals on next contact, same best-effort semantics `ROUTING-PROTOCOL.md` §7 already states |
| Rate limiting | `ROUTING-PROTOCOL.md` §4.4 | ✅ | `core/src/relay.rs` | Per-peer fixed-window limiter (`RateLimitConfig`/`RateLimiter`), bucketed by `now / window_seconds` (deterministic, no wall-clock reads — consistent with the rest of this crate). Defaults (120 envelopes / 2,000,000 bytes per 60s per peer) are **reasoned, not benchmarked** — no target hardware available in this dev environment. Tunable via `RelayEngine::set_rate_limits` / `FfiMeshNode::set_rate_limits`. Over-budget frames are dropped silently (no `Err`, no store mutation, no relay) — disconnect policy is left to the native transport layer |
| Client puzzle | `ROUTING-PROTOCOL.md` §4.5 | ✅ | `core/src/puzzle.rs` | Hashcash-style proof-of-work, `BLAKE3(envelope_id \|\| nonce)` with N required leading zero bits. **Deviation from doc, flagged:** bound to `envelope_id` only, not `(envelope_id, created_at)` — this implementation's `Envelope` has no `created_at` field (only `expires_at`); `envelope_id` already commits to the full envelope content, so this still achieves the doc's goal. Proof travels in `relay.rs`'s `ContactMessage::Data` (not inside `Envelope`'s own wire format) and is solved once by the originator, forwarded unchanged at every hop, cheaply re-verified at each. Difficulty `0` (default) disables it entirely, matching "(tunable/optional)". Default `DEFAULT_DIFFICULTY_BITS = 20` is reasoned, not benchmarked. 5 tests |

| BLE GATT driver | `TRANSPORT.md` §2 | 🚧 | `android/app/src/main/java/india/projectmesh/app/ble/` | Real `android.bluetooth.*` dual-role driver: `BluetoothGattServer` (peripheral: advertise + serve) and per-peer `BluetoothGatt` (central: scan + connect), wired straight to `FfiMeshNode` (not `FfiTransportHub` — that object only logs events, see `ffi_transport.rs`'s doc comment). Two characteristics (one per direction) rather than the doc's implied single characteristic — GATT's data model is inherently asymmetric. 4-byte fragmentation header (message_id/flags/fragment_index) chunks frames to the negotiated ATT MTU (requests 517, falls back to 23). Dual-role connect race (both sides advertise+scan, could double-connect) resolved by a random session-ID tie-break in scan-response service data, since `BluetoothAdapter.getAddress()` can't read a device's own real MAC on modern Android. **Verified:** builds clean, installs, launches without crash, "Start mesh" starts advertising successfully on a real emulator (AVD `mesh_test`, logcat confirms `advertising started`). **Not verified:** an actual two-device BLE exchange (scan discovery, GATT connect, frame exchange) — attempted with a second emulator (`mesh_test2`) but this dev host cannot sustain two headless Android emulators simultaneously (steady 100% CPU, `system_server` ANRs on the second instance even freshly booted, not a stuck-state issue — confirmed by killing and recreating it, which reproduced the same ANR immediately). Real cross-device verification needs either a beefier host or physical hardware. **Deliberate simplifications, not yet addressed:** connections kept open while peers stay in range instead of `TRANSPORT.md` §2.2's short-lived connect/exchange/disconnect cycle (battery cost unaddressed); no backoff/fairness for dense crowds, hardcoded `MAX_CONNECTIONS = 4`; no foreground service (app must stay foregrounded); no BLE-adapter-disabled recovery flow; master key (`FfiMeshNode.open`'s 32 bytes) is `SecureRandom`-generated and stored in plain `SharedPreferences` (`MeshCoordinator.kt`), **not** Android-Keystore-backed as the FFI doc comment calls for — a real, separate outstanding item |

from the code — a stale status table is worse than none.
